# Мікросервіс контролю якості часових рядів енергетичного моніторингу

Мікросервіс приймає вимірювання від енергетичних датчиків, перевіряє їхню якість і зберігає результати в TimescaleDB. Для кожного вимірювання можна дізнатися, які правила спрацювали, чи виконала модель прогноз і чи виявлено аномалію. Перевірити роботу сервісу можна через Swagger UI.

## Які дані приймає сервіс

Один запит `POST /telemetry` містить від 1 до 100 вимірювань **одного зареєстрованого датчика**. Кожне вимірювання має часову мітку з часовим поясом, наприклад `2026-11-24T12:00:00Z`.

| Профіль датчика | Вхідні показники |
|---|---|
| `power` | `value` — активна потужність у кВт |
| `electrical` | `value` — активна потужність у кВт, `voltage` — напруга у В, `current` — струм в А |

Для електричного датчика в кожній точці потрібно передати всі три ключі. Якщо показник відсутній, його значення передають як `null`. Це дозволяє розрізнити дві ситуації: датчик надіслав неповне вимірювання або у часовому ряді пропущено ціле вимірювання.

## Як відбувається перевірка

1. **FastAPI перевіряє запит.** Сервіс перевіряє формат даних, часові мітки та відповідність полів профілю датчика.
2. **Правила перевіряють вимірювання.** Сервіс виявляє вихід за допустимі межі, пропуски, нерегулярні часові інтервали, тривале незмінне значення та надто швидку зміну показника.
3. **Електричний профіль перевіряє узгодженість показників.** Для однофазного датчика сервіс порівнює активну потужність у ватах із добутком напруги та струму. Якщо потужність перевищує розрахункову межу більш ніж на 5 %, точка отримує прапорець `inconsistent_power`.
4. **Isolation Forest шукає аномалії.** Для кожного профілю використовується окрема модель. Прогноз потребує поточної точки, яка пройшла правила, і 30 попередніх придатних вимірювань із регулярним хвилинним інтервалом.
5. **Результат зберігається в БД.** Разом із початковими показниками сервіс записує прапорці якості, деталі перевірок і статус ML. Повторне надсилання тієї самої точки з тими самими значеннями повертає збережений результат.

## Локальний запуск

Потрібні **Python 3.12**, **uv** і **Docker із Docker Compose**. База даних запускається в контейнері, а FastAPI — локально через `uv`. Команди нижче наведено для PowerShell.

### 1. Встановити залежності

Виконати з кореневої папки проєкту, де розташований `pyproject.toml`:

```powershell
uv sync --python 3.12
Set-Location backend
```

Наступні команди виконуються з папки `backend`.

### 2. Налаштувати та запустити базу даних

У файлі `.env` у папці `backend` вказати адресу локальної БД. Для стандартних налаштувань `compose.yaml` використовується такий рядок:

```dotenv
DATABASE_URL=postgresql+asyncpg://telemetry:telemetry@127.0.0.1:5433/telemetry_copy
```

Якщо для контейнера задано власний пароль `POSTGRES_PASSWORD`, його потрібно вказати й у `DATABASE_URL`. Порт підключення **з комп’ютера — `5433`**.

```powershell
docker compose up -d --wait db
uv run alembic upgrade head
```

Міграція створює таблиці та гіпертаблицю TimescaleDB для телеметрії.

### 3. Зареєструвати датчики

```powershell
uv run python -m scripts.backend.seed --sensor-id readme-power-001 --profile power
uv run python -m scripts.backend.seed --sensor-id readme-electrical-001 --profile electrical
```

Команди додають датчики, їхні правила та початковий стан. Ідентифікатор `readme-electrical-001` використовується в прикладі нижче.

### 4. Запустити API

```powershell
uv run uvicorn app.main:app --reload
```

Відкрити [Swagger UI](http://127.0.0.1:8000/docs). У `GET /health` перевірити, що `status` має значення `ready`, а в `loaded_models` є `power-iforest-v1` та `electrical-iforest-v1`.

## Приклад перевірки через Swagger

У Swagger вибрати **POST `/telemetry` → Try it out**, вставити JSON і натиснути **Execute**:

```json
{
  "sensor_id": "readme-electrical-001",
  "points": [
    {
      "timestamp": "2026-11-24T12:00:00Z",
      "value": 0.4,
      "voltage": 230,
      "current": 2
    },
    {
      "timestamp": "2026-11-24T12:01:00Z",
      "value": 5.0,
      "voltage": 230,
      "current": 2
    }
  ]
}
```

Для щойно зареєстрованого датчика очікується **HTTP `200`** і два елементи в масиві `items`.

| Вимірювання | `quality_flags` | `ml_status` | Пояснення |
|---|---|---|---|
| `0.4` кВт | `["insufficient_history"]` | `skipped_history` | Потужність узгоджується з напругою та струмом. Для прогнозу ще бракує історії. |
| `5.0` кВт | `["inconsistent_power"]` | `skipped_rules` | За `230 В` і `2 А` розрахункова межа з допуском становить `483 Вт`. Отримане значення `5000 Вт` перевищує цю межу. |

Після цього в **GET `/telemetry`** можна вказати `sensor_id = readme-electrical-001` і `quality_flag = inconsistent_power`. Сервіс поверне збережене вимірювання з потужністю `5.0` кВт.

## Маршрути API

| Метод | Маршрут | Призначення |
|---|---|---|
| `POST` | `/telemetry` | Прийняти пакет вимірювань і повернути результати перевірки кожної точки |
| `GET` | `/telemetry` | Отримати вимірювання з фільтрами за датчиком, періодом і прапорцем якості |
| `GET` | `/quality-events` | Переглянути зареєстровані події пропуску вимірювань |
| `GET` | `/sensors/{sensor_id}/status` | Перевірити, чи вчасно надходять вимірювання від датчика |
| `GET` | `/health` | Перевірити готовність сервісу, підключення до БД та завантажені моделі |
| `GET` | `/health/live` | Перевірити, чи відповідає застосунок |

Маршрут статусу датчика повертає `awaiting_first_measurement`, `on_time` або `overdue`. Для стандартного інтервалу 60 секунд і допуску 5 секунд датчик переходить у `overdue`, коли від мітки останнього вимірювання минуло понад 65 секунд. Щоб побачити `on_time` у Swagger, потрібно надіслати точку з поточним часом UTC.

## Тести

З папки `backend` виконати:

```powershell
uv run python -m pytest tests/test_bugs.py -v
```

Тести перевіряють обробку часових міток, одноразову обробку пакета, доступність методу блокування стану датчика, відновлення стану під час повторної реєстрації та еталонні прогнози обох моделей.
